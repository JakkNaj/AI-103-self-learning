15 · Authentication credentials, tokens, keys and endpoint wiring

← Revision index

Course lessons: 01.1, 01.3, 02.1; SDK authentication throughout. Question focus: credential class versus identity versus permission.

Three different concepts

  • Identity: who is calling — user, service principal, managed identity.
  • Credential: how SDK code obtains authentication proof.
  • RBAC role: which operations that identity may perform at a scope.

Example: ManagedIdentityCredential obtains a token for App Service's identity; Search Index Data Reader authorizes that identity to query Search. Neither creates the other. Azure authentication overview

Credential classes to recognize

ClassWhat it usesTypical situation
DefaultAzureCredentialA configurable chain of supported Entra credential sourcesSame app code across local development and Azure
AzureCliCredentialAccount authenticated through az loginExplicit local CLI-user authentication
ManagedIdentityCredentialAzure-hosted managed identityDeployed workload without an app-managed secret
EnvironmentCredentialSupported environment configuration, often tenant/client/secretEnvironment-provided service principal credentials
ClientSecretCredentialExplicit tenant ID, client ID and client secretApp/service principal with a secret
AzureKeyCredentialService key that you supplySDK/service supporting API-key authentication

The first five obtain Entra tokens. AzureKeyCredential wraps a key; it does not run az login, request an Entra token or assign roles. credential.update(new_key) replaces its value after rotation. Credential chains, AzureKeyCredential

What DefaultAzureCredential actually does

It tries sources according to the installed library's chain/configuration. Local development may use CLI/other developer credentials; deployment may use managed identity. It does not universally mean “CLI locally, managed identity in Azure”: environment configuration or another enabled source can be selected first.

Identify the credential that succeeded when diagnosing permissions. For a predictable production identity, configure the allowed chain or use an appropriate explicit credential. A user-assigned identity may need its client ID to select it. Obtaining a token does not mean the selected principal can perform the target operation. Chain configuration and diagnostics

Keyless request flow

  1. Enable/select the workload identity.
  2. Assign its required target-service data role at the proper scope.
  3. Configure endpoint, deployment/agent selection and supported credential.
  4. Request an access token for that API's audience/scope.
  5. SDK sends the bearer token; service authenticates it.
  6. Service authorizes the caller's operation; network restrictions must also permit access.

Token audience matters: a token for one API is not automatically valid for another. Use the documented scope for the endpoint in the question. Current Foundry examples can use https://ai.azure.com/.default; direct Azure OpenAI examples can use https://cognitiveservices.azure.com/.default. Do not choose solely from an SDK class name. Foundry authentication contracts

SDK and connection blanks

AIProjectClient(endpoint=project_endpoint, credential=DefaultAzureCredential()) connects to a Foundry project. An OpenAI-compatible client can use a bearer-token provider for Entra authentication, following that endpoint's documented SDK contract. Project SDK versus inference SDK is a client/endpoint decision, separate from the choice of identity.

A connection centralizes an approved external-service reference and authentication configuration. An OpenAPI specification declares the API-key header/scheme; the connection supplies the secret and tool wiring binds it. Keeping a service key in Key Vault does not turn key authentication into managed-identity authentication.

For access to one blob without using an account key, evaluate a user-delegation SAS: Entra-authorized delegation with narrow permissions and short expiry. A SAS is a limited access token, not a new RBAC role; treat the signed URL as sensitive. User-delegation SAS

Diagnose the layer

SymptomFirst investigation
No token can be obtainedCredential availability/configuration; selected identity
401Key/token validity, audience, endpoint/resource/region mismatch
403 after token acquisitionCaller permissions/scope and access restrictions
DNS/connectivity failurePrivate endpoint, DNS, route and firewall
Deployment not foundEndpoint plus deployment/agent identifier

az login authenticates a local user; it does not assign that user a role. Local success does not prove the deployed identity is authorized. Switching to a key may bypass the intended identity design rather than correct its permissions.

Study by decision

  • DefaultAzureCredential & managed identity — 18 questions. DefaultAzureCredential is a supported credential chain; use managed identity where deployed and pair it with required data permissions.
  • AzureKeyCredential & secret storage — 2 questions. AzureKeyCredential wraps a provided key. Store/rotate required secrets using appropriate configuration rather than prompts/source code.
  • Token audience, region & 401 vs 403 — 4 questions. Align token scope/audience, credential, endpoint and resource. Investigate credential/audience/expiry for 401 and caller/data permissions for 403.
  • Project clients, deployments & environment — 15 questions. Use the documented project endpoint and credential. Obtain the supported inference client and send the configured deployment identifier.

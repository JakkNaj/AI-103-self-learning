07 · Content Understanding: analyzers, schemas and grounded output

← Revision index

Course lessons: 04.4–04.6. Question focus: analyzer creation, output type, asynchronous analysis and version-sensitive modes.

What an analyzer defines

An analyzer is a reusable configuration for interpreting supported content and producing the required representation. Inputs can include documents, images, audio or video, according to the analyzer's supported modality and API. Define business fields using types and descriptions; select a prebuilt analyzer or configure a custom one.

Custom analyzers can start from natural-language field descriptions without first training a Document Intelligence model on labeled examples. They still need representative validation. One business schema does not imply that every modality can be supplied in every request shape. Content Understanding overview

Setup and execution are separate

  1. Choose API version, supported modality and an appropriate base/prebuilt analyzer.
  2. Define typed fields, clear descriptions and any controlled category set.
  3. Configure content extraction, model dependencies and supported evidence/confidence settings.
  4. Create the analyzer; wait for readiness where creation is asynchronous.
  5. Analyze a new supported input with that analyzer ID.
  6. For asynchronous analysis, follow Operation-Location and poll to success/failure.
  7. Read content/fields; preserve provenance; validate values against the source.
  8. Review uncertainty or missing evidence; feed only validated representations downstream.

Code blanks: analyzer ID selects the processing definition; input URL/bytes supplies the evidence; operation URL tracks one job. They are not interchangeable. A 202 response means accepted, not finished.

Polling applies to asynchronous analyze operations. Current preview Read/Layout operations also include synchronous alternatives; do not memorize “every Content Understanding call must be polled.” REST quickstart, release changes

Time-aligned video/audio segmentsLocate claims or events in original mediaStart/end times, transcript and relevant visual evidence

Field intent can differ: extract an evidenced value; classify into categories; generate a derived description/summary. Descriptions must specify what to do when evidence is absent. A normalized total invented to fill a schema is still wrong. Grounding points back to evidence; it does not automatically prove every inference.

Modality trap: current documentation limits confidence scores to document files. Do not assume that an image/audio/video field has all document confidence/source capabilities. Support for document confidence/grounding has also expanded across field methods; an older “extract-only” claim may be outdated. Current release notes

Historical standard/pro versus current agentic mode

Version/wordingInterpret it as
Historical 2025-05-01-preview, standardOrdinary extraction; simpler/high-volume tasks
Historical proAdditional reasoning, multiple-document support and reference knowledge
Current 2026-06-01-preview, agenticAdvanced reasoning over document evidence; config.workflow="agentic"

The April exam outline still uses single-task/pro terminology. Our ExamTopics #5 reflects that historical distinction. Keep its conceptual choice — inexpensive extraction versus advanced reasoning — but do not assume the old configuration is valid today.

Current agentic preview supports one input file per request, which may contain several logically related documents. It is useful for cross-section reasoning, calculations and validation. It does not mean unlimited separate input files. For straightforward fields, a standard analyzer is the simpler starting point. Historical modes in release notes, current agentic mode

Common distractors

  • Training a classifier alone does not define the requested extraction fields.
  • Search ranking does not create analyzer output.
  • Markdown is useful for reasoning; it is not a substitute for a typed business contract when JSON fields are required.
  • Stripping pages/timestamps makes clean output less verifiable.
  • A successful job still needs value validation; low confidence may require review rather than automatic approval.

Study by decision

  • Reusable analyzers & typed field schemas — 22 questions. Define a reusable analyzer with supported inputs and a typed schema; describe extraction/classification/generation intent and test representative inputs.
  • Markdown, fields & source evidence — 9 questions. Keep Markdown/content for readable document structure, typed fields for business integration, and supported source evidence for review.
  • Historical standard/pro vs agentic mode — 5 questions. Read the API/date context. Historical standard/pro questions retain their archived meaning; current agentic configuration belongs to its documented preview version.
  • Content Understanding async analysis — 4 questions. Poll the documented operation URL until success/failure; read results only after successful completion.
  • Grounding, confidence & object regions — 5 questions. Check supported metadata for the actual modality/API. Region evidence needs explicit supported location output.

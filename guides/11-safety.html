Direct versus indirect prompt injection

Direct: an instruction in the user's prompt tries to override the intended rules. Indirect: an instruction arrives inside evidence — webpage, PDF, image text or tool output.

Retrieved material is task data, not authority to change system instructions. An attack can be ordinary-looking text; it need not contain violence or sexual content. Conversely, a harmful image need not contain any prompt attack. Prompt Shields

Layered processing: exam sequence

  1. Authenticate the user and restrict source/tool access.
  2. Classify relevant harmful input content.
  3. Inspect untrusted grounding content for indirect attacks using the supported integration.
  4. Exclude/block detected attack content before sending it as evidence.
  5. Generate within task constraints and validate output.
  6. For a requested action, validate arguments and enforce permission/approval.
  7. Execute only the approved operation; check actual success.
  8. Record a minimized, correlated audit trail and monitor failures.

For image text consumed by the model, preserve the trust boundary through OCR/extraction. Use the attack-detection API's supported content representation; a document-text request does not automatically accept raw image pixels.

Example: uploaded screenshot contains disturbing imagery and text telling the agent to export files. Image moderation addresses visual harm; indirect-attack handling addresses embedded instructions; backend tool permissions prevent export. Each closes a different route.

Why several Yes/No answers can all be No

ExamTopics #23–26 give the same two-risk scenario but propose one control at a time. User Prompt Shield, image moderation, document Prompt Shield and protected-material detection each fail to satisfy both risks by themselves. “Useful control” does not mean “complete solution to every stated requirement.”

Protected-material detection concerns protected text/code; it is not a replacement for image harm moderation or prompt-injection protection. A watermark can support a policy/provenance requirement without proving the image is safe or authentic.

Approval and tool safety

Approval must cover the action and arguments before the side effect. Rejecting approval means the action must not run. If material arguments change, apply the policy to the changed action rather than reuse an unrelated approval.

Use scoped credentials, allowed-tool lists and server-side checks. Read-only agents should not have executable delete permissions merely because the MCP server exposes deletion. A prompt saying “never delete” is weaker than removing that authority.

Retries of consequential operations require backend-supported idempotency. Logging an accidental duplicate records damage; it does not prevent it. Human review, deterministic constraints and stop budgets remain necessary where the task requires them. Tool best practices

Responsible AI lifecycle

Identify/map potential harms → measure with representative and adversarial cases → mitigate across model, safety system, instructions/grounding and user experience → release under oversight → monitor/update. Tune thresholds using false positives and missed harms. No single threshold guarantees all safety outcomes.

Redact/minimize PII before ordinary diagnostic propagation, while preserving enough identifiers/timing to investigate. Restrict any necessary raw evidence and enforce retention/deletion. PII overview

Study by decision

  • Harm categories & Content Safety policy — 18 questions. Use supported moderation capabilities and configure enforcement/thresholds; evaluate both unsafe escapes and unnecessary blocking.
  • Direct vs indirect prompt injection — 20 questions. Treat retrieved/media instructions as untrusted data. Apply the relevant Prompt Shields input/document checks and block/remove detected attack content as required.
  • Human approval & publication authority — 14 questions. Pause before the consequential action; bind approval to the exact validated action/asset and proceed only after the required approval.
  • Backend authorization & tool allowlists — 21 questions. Enforce caller/resource ownership, allowed operations and least-privilege runtime credentials in trusted backend code.
  • Retries without duplicate side effects — 4 questions. Use an idempotency identifier and backend deduplication/operation-state checks before safe retries.
  • Bound autonomous loops — 1 questions. Add execution/time/token budgets, stop conditions and escalation criteria.
  • Brand symbols, watermarking & disclosure — 8 questions. Add the explicit brand/disclosure checks and required watermark to the release workflow.
  • Private diagnostics & log redaction — 5 questions. Redact/minimize sensitive content before ordinary logging; keep safe correlation and tightly controlled necessary diagnostics.

Applications can also push already processed documents directly into an index; an indexer is not mandatory for every design. Indexers, knowledge store

Runtime ingestion order

  1. Indexer reads the configured source.
  2. Document extraction exposes text and, if configured, normalized images.
  3. OCR/enrichment obtains missing content; preserve source locations.
  4. Split content into useful chunks, preferably respecting headings/tables.
  5. Generate an embedding for each chunk.
  6. Map/project chunk text, vectors and parent metadata into the index.
  7. Check failures and freshness; rerun/schedule ingestion and handle deletion.

Configuration order differs: create the index, data source and skillset, then create an indexer referencing them. An exam asking how data flows is testing runtime order, not necessarily resource-creation order.

For integrated vectorization, Text Split skill → Azure OpenAI Embedding skill is a common pair. At query time, use an index vectorizer or supply an application-generated query vector. Document and query embeddings must use compatible model/version/dimensions; equal dimension counts alone do not prove compatible vector spaces. Integrated vectorization

Mappings and projections

  • fieldMappings: source fields → index fields.
  • outputFieldMappings: skill/enrichment outputs → index fields.
  • indexProjections: one parent → many searchable child chunks, repeating needed parent metadata.

If enrichment produced key phrases but they never reach the index, inspect output mapping. If each chunk must become its own document with parent ID/revision, inspect index projections. Preserve unique chunk IDs, text, source URL/page, revision, tenant/access metadata and vectors. Output mappings, index projections

To expose embedded images for OCR, configure a suitable non-none imageAction, such as generateNormalizedImages; downstream skills commonly use /document/normalized_images/*. Semantic ranking cannot recover images that ingestion never extracted. Image processing

Ranking happens at query time

Search stageWhat it doesExam clue
Keyword / BM25Lexical matchingExact names, terms, product codes
Vector / nearest-neighbor searchEmbedding similarity; HNSW is an approximate-search algorithmParaphrases or meaning
Hybrid / RRFCombines keyword and vector result rankingsExact IDs plus conceptual queries
Semantic rankerReranks retrieved text-rich candidatesImprove ordering of already found evidence

Semantic ranker is not the embedding model and does not replace initial retrieval. RRF combines ranked lists; it is not a vector distance metric. Search scores and reranker scores describe different stages. Hybrid search, semantic ranker

For exact tenant IDs, use an appropriate string metadata field with filtering; a full-text analyzer is not an authorization mechanism. Punctuation-heavy product identifiers may need an exact-token analyzer such as keyword_v2. An existing field generally cannot have filterable switched in place: add/populate a suitable field or rebuild the index. Index schema, custom analyzers

Enforce filters before evidence reaches the model

Determine allowed tenant/documents server-side, then apply those restrictions to retrieval. For a question explicitly requiring exclusion before vector candidate selection, choose vectorFilterMode="preFilter". Use a filterable field and an authenticated caller mapping. A tenant ID supplied by the model/user must not independently establish entitlement.

Post-answer filtering or “ignore other tenants” in a prompt cannot undo exposure of private context. Also filter validity dates/market/revision where required. Vector filtering

Diagnose the earliest failing stage

Empty text from scans → OCR/extraction. Missing new files → indexer run/ingestion. Old prices → update/delete handling. Wrong top results → chunking/embedding/query/filter/ranking. Good retrieval, bad answer → generation. 403 → caller's data role. Failed embeddings → embedding endpoint/identity/quota.

Study by decision

  • Keyword vs vector vs hybrid retrieval — 16 questions. Keyword retrieval handles literal terms; vectors retrieve by similarity; hybrid combines both result sets.
  • Hybrid RRF & semantic reranking — 14 questions. Hybrid search fuses result lists with reciprocal rank fusion; optional semantic ranking reranks supported text-rich candidates.
  • Indexer & integrated vectorization order — 24 questions. Configure data source, indexer, skillset and index. Extract usable content before chunking, create embeddings, and map/project output into the index.
  • Layout, chunk size & overlap — 11 questions. Chunk by usable document structure; preserve headings/tables and relevant metadata. Tune size and overlap to retrieval evidence.
  • Vector fields & embedding consistency — 3 questions. Align vector field dimensions/profile and stored/query embedding model/configuration. Re-embed when changing incompatible vector spaces.
  • Child chunks, mappings & knowledge stores — 5 questions. Use field/output mappings for index fields, index projections for child chunk documents, and knowledge-store projections for storage outputs.
  • OCR, normalized images & custom skills — 11 questions. Expose normalized images when needed, run OCR/layout extraction before downstream text skills, and satisfy the custom skill request/response contract.
  • Tenant filters & permission trimming — 10 questions. Store filterable authorization metadata; enforce caller-specific filters in retrieval, including the required vector-filter stage.
  • Index freshness & ingestion failures — 11 questions. Check ingestion schedules, last successful runs, errors, source updates/deletes and indexed metadata before changing prompts.
  • Search query code & result counts — 4 questions. Read the actual query: search_text adds keyword retrieval, vector queries add similarity, top shapes final results and k controls vector candidates. Exact identifiers need appropriate analysis.

Build the workflow in order

  1. Define each agent's role, goal, inputs and expected output.
  2. Establish dependencies: fixed stages, independent branches, discussion or transfers.
  3. Define nodes and edges; save outputs needed by later nodes.
  4. Validate data and apply deterministic business rules.
  5. Pause for approval where the rules require it.
  6. Execute the approved operation; save its result.
  7. Merge or summarize evidence; check contradictions and missing results.
  8. Stop on completion, rejection, failure or a configured limit; retain correlated traces.

Example: extract refund amount → validate eligibility → if above threshold, obtain approval → issue refund → report actual outcome. “Notify the supervisor after issuing it” fails an approval requirement. “The model thinks it is safe” also fails it.

For a mandatory sequence and conditional branching, use explicit workflow control. A prompt asking agents to follow an order is weaker than enforcing that order in the graph. A deterministic rule engine can decide eligibility while the model explains the decision. Human-in-the-loop workflows

Reflection is a quality step

Draft → critique against stated criteria/evidence → revise → evaluate → stop or escalate. Bound the revision count. A critic can identify unsupported claims, but its own claims also need evidence. Neither self-critique nor a high evaluation score supplies human publishing authorization.

A persisted agent definition stores the agent's configuration; it is not every customer's conversation. Keep conversation IDs separate per customer. Reuse a framework session for related turns; creating a new session on every call loses that continuity. Memory needs an authenticated user scope, retention and deletion controls. API recognition: Responses can link response IDs or use conversations. Chat Completions uses a supplied message history. A framework can manage that history and tool loop through its configured client. It does not make authorization, memory isolation or business validation automatic.

Workflow expressions and publishing

In the course's Foundry workflow expression questions, a local variable is referenced as Local.Var01; Upper(Local.Var01) uppercases it. A nonempty check can use !IsBlank(Local.Var01). System. refers to system variables. Exact node/YAML syntax belongs to the workflow version shown in the question.

Publishing to an agent endpoint or Microsoft 365 is a separate lifecycle step: test the configured agent → verify publishing rights and target channel → publish the selected version → configure distribution/audience → test with the intended user → monitor. Publishing permission and downstream tool permissions belong to the identities actually used. A developer's successful test does not prove an end user's deployment will work.

Study by decision

  • Sequential dependencies — 9 scored questions. Use sequential orchestration when later stages depend on earlier outputs.
  • Concurrent specialists — 3 scored questions. Run independent specialists concurrently; merge only after their required results are available.
  • Handoff & routing criteria — 10 scored questions. Use explicit handoff criteria and configured routes to transfer the active task to a specialist.
  • Group chat & review — 2 scored questions. Use group chat when agents exchange messages under speaker-selection and stopping rules.
  • Magentic planning — 2 scored questions. Use adaptive planning that updates a task ledger as new evidence arrives.
  • Compare orchestration patterns — 3 scored questions. Identify dependency, independence, control transfer, discussion, or changing plan before selecting a pattern.
  • Deterministic workflows & branching — 10 scored questions. Use explicit workflow nodes, validated state, conditions and gates for a predictable process.
  • Power Fx workflow variables — 2 scored questions. Match the variable scope and function to the saved workflow value; test expressions against the actual node context.
  • Conversation state & API turns — 10 scored questions. Keep the relevant conversation identifier or message history for the same user/session. Recognize Conversations/Responses versus client-managed Chat Completions history.
  • Durable user memory & isolation — 18 scored questions. Use per-user durable memory scopes with access controls and retention policies. Keep enterprise knowledge in retrieval storage.
  • Reflection & critic loops — 3 scored questions. Bound revision loops and validate corrections against evidence and independent criteria.
  • Agent creation, versions & streaming — 3 scored questions. Use the documented SDK/API for the agent version, conversation, and streamed response event.

03 · MCP versus A2A

← Revision index

Course lessons: 02.3, 02.9, 03.2, 03.5. Basis: existing question banks; primary documentation checked 2026-10-05.

  • MCP: application/agent accesses tools and context through a standard protocol.
  • Host = AI application; client = connector; server = exposes tools/resources/prompts.
  • tools/list discovers tool schemas; tools/call executes a selected tool.
  • Typical transports: stdio locally, Streamable HTTP remotely. MCP architecture
  • A2A: communication/delegation between independent agents; Agent Card advertises capabilities and endpoint. A2A course module

3.1 Client-mediated MCP: the extra steps in the course lab

Here, your application is the bridge between the model and MCP server:

  1. Connect: start/connect to the MCP server and create a client session.
  2. Initialize: perform the initialization/capability exchange required by the course SDK/version.
  3. Discover: await session.list_tools() gets tool names, descriptions and input schemas; it does not execute the business operation.
  4. Adapt/register: expose those tools to the model as function definitions; map MCP inputSchema to function parameters and keep a name-to-implementation dispatch map.
  5. Request: send the prompt to the agent; inspect the returned function calls.
  6. Execute through MCP: parse/validate/authorize, then await session.call_tool(tool_name, arguments).
  7. Return and continue: serialize the MCP result into the function-result envelope required by the model API, preserving the original function-call ID; submit it and process the next model response.
  8. Close resources: keep the session alive while calls run; close it after awaited operations finish.

Three hops: model requests a function → application calls MCP → application returns MCP evidence to the model. The returned MCP content may contain multiple text/image/structured blocks; handle the relevant blocks rather than assuming the first block is always the complete result. MCP architecture

3.2 Managed remote MCP: a different execution path

Configure the remote endpoint, authentication connection, allowed tools and approval policy; the service can perform discovery and calls. Your app need not implement session.call_tool for this integration.

If approval is required, a Foundry response can contain mcp_approval_request. Review it, then submit mcp_approval_response with approval_request_id set to the request item's id, plus the approval decision; continue from the appropriate response/conversation. This is an approval response, distinct from a local function's function_call_output. Managed MCP and approval

In the OpenAI Responses remote-MCP integration, mcp_list_tools records discovered tools and mcp_call records a tool invocation. Their names differ from a client-mediated function wrapper's function_call. Official OpenAI MCP integration

3.3 A2A: discover and delegate to an independent agent

  1. Obtain the agent's Agent Card: identity, capabilities/skills, endpoint and supported authentication information.
  2. Decide whether its advertised capability matches the task.
  3. Authenticate and send a request using the supported protocol/client.
  4. Handle task state: work may continue asynchronously or require additional input.
  5. Collect returned artifacts/results and pass relevant evidence into the parent workflow.
  6. Enforce timeout/termination rules; retain correlation and source-agent information.

The card advertises authentication requirements; it does not authenticate a caller or grant authorization. An asynchronous task ID is not automatically the completed answer. A2A integration still needs a parent orchestration policy; discovery does not choose all handoff/approval rules for you. A2A course module

Custom extraction training: order matters

  1. Collect representative samples of the document type, including meaningful variants.
  2. Store accessible training files and label the fields/tables to extract.
  3. Build the chosen template/neural model.
  4. Evaluate on separate samples; inspect errors and confidence by field.
  5. Improve data/labels if needed; record the resulting model ID.
  6. Use that model ID in analysis requests for new documents.

Training learns a custom extraction model. Analysis applies an existing model. Calling analyze with a document does not train the model on that document. A model ID identifies the extractor; the input document's URL/path is a different value.

Document analysis: complete client workflow

  1. Construct the appropriate SDK client with matching endpoint and credential.
  2. Choose the model ID and supported input representation: URL or bytes/stream.
  3. Submit analysis.
  4. Wait for completion: SDK poller or REST operation URL.
  5. Read the completed document fields/content/tables and supported locations/confidence.
  6. Validate required fields, arithmetic, dates and confidence; route uncertain results for review.

In Python, a begin_analyze_document(...) call returns a poller. poller.result() waits and obtains the final analysis result. In REST, an accepted asynchronous request supplies an Operation-Location; poll that operation until a terminal state. Check failure before consuming fields. Exact request keywords differ across SDK versions. SDK/REST workflow

REST recognition: v4 GA uses api-version=2024-11-30; the analyze operation includes documentModels/{modelId}:analyze. prebuilt-layout is a model ID, not a source URL or a training mode.

Classification and composition

For mixed intake: identify type → route to the corresponding extraction model → validate its fields. A scanned file may contain multiple logical documents; splitting and classification must match the intended page boundaries.

Version trap: v4 composition uses an explicitly trained classifier with extraction routes. Older composition descriptions use an implicit classification step. Do not transfer the older setup verbatim into a v4 code question. The composed ID exposes the routed collection; the result's document type tells you what was classified/extracted. Composed models

Common distractors

  • OCR only: obtains characters, not all field semantics or layout relationships.
  • Classifier only: identifies document kind, not invoice totals.
  • Custom neural without labels: not the standard supervised custom-training workflow.
  • High confidence: useful review signal, not guaranteed factual/business correctness.
  • Image generator: creates pictures rather than reading real document evidence.
  • Universal multimedia extractor: Document Intelligence is document-focused; use Content Understanding for broader schema-driven audio/video/image intake.

Example: standard supplier invoice → try prebuilt invoice. Company-specific application forms with varying layouts and labeled fields → custom neural. Invoice plus receipt plus application mixed intake → classify and route.

Study by decision

  • Read vs Layout vs prebuilt invoice — 13 questions. Read extracts text; Layout preserves structure/tables/selection marks; prebuilt invoice targets common invoice fields.
  • Custom template vs neural extraction — 4 questions. Evaluate template extraction for consistent layouts and neural extraction for varied layouts sharing semantic fields.
  • Classifier & composed-model routing — 2 questions. Use the classifier/composition workflow documented for the target API version to route types to extraction models.
  • Document analysis pollers — 2 questions. An SDK poller represents asynchronous analysis; obtain its completed result and handle failure.
  • Document REST inputs & query fields — 4 questions. Match the model ID, request source and optional query fields to the selected Document Intelligence API.

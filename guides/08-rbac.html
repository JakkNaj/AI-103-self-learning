08 · RBAC: caller, operation and scope

← Revision index

Course lessons: 01.1, 02.1, 02.5, 04.8; applies throughout. Question focus: least privilege and the identity actually making each request.

Solve a role question in this order

  1. Who calls? Developer, application identity, project identity, published agent or connected service.
  2. What operation? Invoke agent, infer model, create deployment, query index, write documents or read Blob.
  3. Which endpoint/resource? Foundry project, one agent, direct OpenAI resource, Search or Storage.
  4. Which role family grants that action? Management permissions and data permissions differ.
  5. At which scope? Choose the narrowest scope satisfying the requirement.

Authentication establishes identity; RBAC authorizes actions. DefaultAzureCredential is a credential class, not an RBAC role. A private endpoint is a network path, not authorization. Authentication/authorization

Foundry project/agent access uses its own role family. An endpoint described as OpenAI-compatible does not automatically establish which resource/role family the question targets. Search management rights do not automatically provide document-read rights. Search roles, Blob data roles, direct Azure OpenAI roles

General Owner / Contributor / Reader primarily address Azure resource management. Contributor does not grant role assignment, and a management assignment does not automatically satisfy a service's data actions.

Trace the identity at every hop

Example: user invokes agent → agent queries Search → analyzer reads Blob.

The caller invoking the agent needs agent access. The identity executing retrieval needs Search data access. The identity reading the blob needs Blob data access. Those may be three different principals. Giving the developer every role leaves a deployed service's 403 unresolved.

A shared connection centralizes configuration/credential references. It does not automatically grant all projects unrestricted administration or make every downstream identity identical. For isolated published-agent tool access, identify the agent's configured runtime identity and assign its target-service permissions separately.

CLI and diagnostics

Role-assignment blanks generally require principal, role and scope. A principal/object ID identifies the assignee; a client/application ID selects an application or user-assigned managed identity in authentication settings. Match the parameter being filled.

Token obtained, request returns 403 → inspect data actions, scope, actual caller and other access conditions. 401 → first inspect credential/token audience/expiry/endpoint. Network/DNS failure → first inspect connectivity. These are diagnostic starting points, not universal explanations for every status.

Common distractors

  • Subscription Owner for a read-only app: unnecessarily broad and not an automatic substitute for data actions.
  • Foundry User for someone only invoking one agent: consider narrower Agent Consumer.
  • Search Service Contributor for query-only access: wrong permission layer.
  • Assigning a role to the project identity when App Service performs the call: wrong principal.
  • Resource key in Key Vault: protects key storage, but does not meet a strict “keyless managed identity” requirement.

Study by decision

  • Foundry invocation vs development roles — 6 questions. Agent Consumer grants agent interaction; Foundry User supports project development/testing. Choose the supported narrow scope.
  • Publishing role & scope — 2 questions. Current Foundry guidance requires at least Foundry Project Manager at Foundry resource scope for publishing.
  • Search data vs management roles — 4 questions. Search Index Data Reader queries documents; Index Data Contributor writes document data; Search Service Contributor manages Search objects.
  • Blob permissions & short-lived delegation — 2 questions. Use Blob Data Reader for read-only blob data. For keyless time-limited delegation, evaluate a user delegation SAS with the needed permissions.
  • Subscription quota visibility role — 3 questions. Cognitive Services Usages Reader at subscription scope grants the documented narrow quota/usage visibility.
  • Actual caller, scope & 403 — 5 questions. Trace the principal making each hop, required data action and applicable scope. Assign permissions to that principal.
  • Role assignment CLI & principal IDs — 2 questions. Fill the actual principal/object ID, role definition and resource/project/agent scope for the requested assignment.
  • Shared connections & isolated access — 3 questions. Share governed configuration at the appropriate resource/project boundary while preserving narrow project and runtime permissions.

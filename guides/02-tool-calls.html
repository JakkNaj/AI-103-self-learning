02 · Tool calls — detailed exam workflow

← Revision index

Course lessons: 01.3, 01.4, 02.1, 02.2, 02.7. Basis: existing question banks; primary documentation checked 2026-10-05.

Define/register → request → inspect/parse → validate/authorize → execute → package result → submit/continue → final answer or another tool call.

The questions test different parts of this lifecycle. A tool definition, a requested call, an executed operation, and a returned result are four different things.

2.1 Complete sequence: setup plus execution

StepWhat happensExam clue
1. Implement and describe the toolWrite the function; define its name, description and parameter schema.“Define a function”, “complete the schema”.
2. Register/configure itAdd the definition to the agent or request's tools; configure credentials/connections as needed.“Make the tool available to the agent”.
3. Send the user requestCall the model/agent with the available tools and conversation context.“Send the prompt and tool schemas”.
4. Inspect the model outputDetect requested calls; read each name, serialized arguments and call identifier.“The model proposes a function call”.
5. Parse and validateDecode JSON; check the function name, argument types/values, caller permissions and any required approval.“Before executing”, “authorized operation”.
6. Dispatch and executeInvoke the matching implementation with the approved arguments; capture its actual result/error.“Application-side execution”.
7. Package the resultBuild the API-specific tool-result item linked to the original call ID.“Correlate the output”, “return the function result”.
8. Submit and continueMake the follow-up model request with results and preserved context. Handle further calls if requested.“Continue the conversation”.
9. Read the final answerThe model uses tool evidence to compose the user-facing response.“Final response”, “synthesize the answer”.

The model requests a custom function; the application/runtime executes it. Returning the function's result is followed by another model turn. Microsoft function calling

2.2 Ordering questions: identify where the question starts

  • Whole interaction: send prompt + tool schemas → receive requested call → validate/authorize → execute → return correlated result → request the model's answer.
  • “After receiving a tool request”: read name/arguments + retain call ID → parse/validate/authorize → execute → return correlated output → continue model processing.
  • “The function has already executed”: package and submit its output with the original call ID; execution is already complete.

Example: user asks for ticket status → model requests lookup_ticket → app parses ticket_id → checks access → queries the ticket system → sends the status with the matching call ID → model explains it to the user. More tool calls can follow before the final answer. Official OpenAI function-calling flow

Two IDs to keep separate in Responses:

  • item.call_id identifies one function invocation; copy it into that function's result.
  • response.id identifies the whole model response; use it as previous_response_id for continuation.

For conversation context, use a linked previous response, a persistent conversation ID, or manually maintained input history. Manual history must retain the relevant model output items as well as tool results. With response chaining, resend stable top-level instructions; they aren't inherited through previous_response_id. 2.4 Code-completion questions: schema versus actual arguments

KeywordMeaning
parametersDefinition of the tool's accepted input schema.
type: "object"Arguments are a named-field JSON object.
propertiesDeclares field names, types and descriptions.
required: ["ticket_id"]The argument object must contain this field.
enumRestricts a field to listed values.
additionalProperties: falseRejects undeclared fields.
argumentsActual values proposed by the model, commonly a JSON-encoded string.

json.loads(item.arguments) decodes the requested arguments into a Python object. json.dumps(result) serializes an application result for submission.

In strict function schemas, every property must be listed in required, with additionalProperties: false on objects; optional values can be represented with a nullable type. Schema conformity does not establish business permission. Structured outputs and function schemas

One Responses tool-execution round after receiving a response: schematic Python; dispatch_validated is your application's helper, not an SDK method. It checks the allowed function, inputs, permissions and approval before dispatching.

import json

outputs = []  # Fresh results for this model response.
for item in response.output:
    if item.type != "function_call":
        continue

    arguments = json.loads(item.arguments)
    result = dispatch_validated(item.name, arguments)
    outputs.append({
        "type": "function_call_output",
        "call_id": item.call_id,
        "output": json.dumps(result),
    })

if outputs:
    response = client.responses.create(
        model=model_deployment,
        previous_response_id=response.id,
        input=outputs,
        tools=tools,
        instructions=agent_instructions,
        tool_choice="auto",
    )

Repeat the inspection/execution round if the next response requests more functions; apply application stop limits. Handle every requested call, keeping each result's ID. A response containing only calls may have no final output_text yet. Function-call output handling

2.5 Tool selection: three different meanings of “required”

SettingMeaning
Schema required: ["ticket_id"]This argument field must be present.
tool_choice="auto"Model may answer directly or request tools.
tool_choice="none"Tool use is disabled for this response.
tool_choice="required"At least one available tool must be used.
Responses tool_choice={"type": "function", "name": "lookup_ticket"}Force the specified function, where supported.

Exam phrasing matters: “use a tool” can be satisfied by required. “Always retrieve before answering” needs the particular retrieval operation guaranteed, through an appropriate tool restriction/selection or an explicit workflow step. With retrieval and calculator both available, required alone can select the calculator.

After the required lookup has completed, a follow-up request can use auto to permit the final answer. Requiring another tool on every manual-loop continuation can keep requesting tools unnecessarily. Chat Completions' named-function selector uses the nested function: {"name": ...} form. Tool-choice behavior, Chat Completions selector

Source wording trap: ExamTopics #14 displays tool_choice={“required”}. The intended setting is tool_choice="required"; the displayed braces/quotes are not valid parameter syntax for that intended value.

2.6 OpenAPI questions: API description plus credential wiring

Describe operations → configure authentication → bind the project connection/identity → register the tool → invoke.

  • Each callable operation needs a unique, descriptive operationId, a usable input schema and the correct external endpoint.
  • For an API-key header, the specification declares components.securitySchemes → type: "apiKey", in: "header", name: "x-api-key" (use the API's actual header name); a security requirement applies that scheme.
  • The project connection stores the secret; the tool's authentication configuration must reference that connection. A schema describes how to send a key; it does not supply the stored value by itself.
  • A missing key header / 401 points to authentication wiring, connection selection or header-name mismatch. Changing prompts or model temperature does not repair it.
  • Managed identity requires an appropriate target-service role for the identity actually making the tool request.

Why #16 and #21 have different answers: #16 asks what to configure in the specification → API-key security scheme. #21 asks how the tool obtains the secret from Connection1 → bind that connection. Both are parts of the same integration. Microsoft OpenAPI integration

2.7 Execution, approval and diagnostics

  • Custom function: application/framework invokes the implementation. Managed tools: the service can execute supported built-in, OpenAPI or remote MCP integrations. Read the setup to identify the executor.
  • Approval gates a consequential operation before execution. Logging afterward provides an audit record, not approval.
  • If a write operation times out after possibly succeeding, use a stable idempotency key for the intended action, backed by backend deduplication, when retrying. Retrying a non-idempotent operation can repeat its side effect. Retry considerations
  • An automatic framework loop still needs safe implementations, scoped credentials, runtime validation and connection lifecycle management. Tool best practices
  • Tracing shows the ordered LLM/tool spans, arguments/results when recorded, timings and failures for a particular run. It helps distinguish “tool wasn't called”, “tool failed”, and “tool succeeded but the model answered poorly”. Aggregate token/latency metrics cannot show the entire individual sequence. Agent tracing

Frameworks can manage history, but reuse the session across turns; session state and tool-call/result correlation are separate concerns. Sessions

Study by decision

  • Function schemas & argument contracts — 15 questions. Declare meaningful tool names/descriptions and bounded JSON parameter schemas; validate arguments again in the backend.
  • Function-call execution loop — 12 questions. Provide schemas → receive/parse → validate and authorize → execute → return correlated output → continue model processing.
  • call_id vs response.id — 3 questions. Return the tool output under its original call_id. Use the appropriate response/conversation identifier for API continuation.
  • OpenAPI authentication & connections — 4 questions. Describe the API key location/header and security requirements; bind the actual credential through the tool connection/auth configuration.
  • OpenAPI operations & safe contracts — 3 questions. Use supported OpenAPI versions, unique operation IDs, clear descriptions, bounded inputs and safe backend behavior.
  • File search, enterprise search & code tools — 23 questions. File search retrieves uploaded knowledge; Search tools access enterprise indexes; a sandboxed code tool computes over data.
  • Required tool vs required retrieval — 7 questions. Required means at least one allowed tool is called. Guarantee a particular retrieval with a supported tool selector or an explicit workflow prerequisite.
